# Data-only computation configuration nomination

`nomad.recursion.prepare_computation_experiment` adds a bounded nomination path to the existing candidate-only RECURSION module. It does not replace the running engine, import a candidate program, execute a learner, edit WITNESS, open evaluation contracts or qualify native isolated self-revision.

The trusted temporal harness predeclares exactly three profiles: `standard`, `long` and `short`. Their commitment, credit horizon and detector settings are fixed before development is measured. The baseline is `standard`. The selection rule is the harness's minimum mean development log loss plus `2 × total measured process CPU / 512`; ties follow declared profile order. No additional configurations are searched by the nomination step.

The input must be a bounded, complete, current-source prospective development receipt. The shared read-only harness validator checks the registered trial inventory, all worker completion/cleanup receipts, raw output hashes, trace-derived scores, matched inputs, actual configurations, complete measured CPU arithmetic and source bindings. The preparer additionally refuses duplicate JSON keys/nonfinite constants, checks that the input remains byte-identical during validation, and binds its own implementation. A status string alone cannot establish eligible development evidence.

Run preparation after the final development run and before independent evaluation:

```powershell
py -3 -B scripts\prepare_temporal_self_revision_v18.py --development results\TEMPORAL_DEVELOPMENT_V018.json --output experiments\computation_candidate_TEMPORAL_V018
```

Every output path must be new. The directory contains only JSON data: baseline settings, nominated settings, the exact baseline rollback settings, development selection/metrics and a checksummed protocol. The protocol binds the raw development report, registered profiles, current implementation and every generated file. Publication uses the existing bounded staging routine and refuses existing destinations and link/reparse paths.

The optional `--future-plan-sha256` accepts only a digest commitment; it never opens a future plan or hidden data. Without that commitment, a changed development winner is `DEVELOPMENT_NOMINATION_ONLY`. A supplied digest permits `PREPARED_NOT_RUN`, with independent acceptance still HOLD. If standard wins, the artifact says `BASELINE_RETAINED`, records identical baseline/candidate settings and claims no development improvement or eligibility gain.

A development-selected configuration is a research proposal. The prospective experiment must independently test its registered quality/cost hypothesis. Any claim about native engine self-revision additionally requires real qualified containment/recovery, independent baseline/candidate observations, full regressions and the existing protected-source acceptance rules. This data-only artifact satisfies none of those gates by itself. `self_improvement_advantage` remains `NOT_ESTABLISHED` and `production_promotion` remains `HOLD`.

Five new artifact tests and four existing ranking-proposal tests passed. Positive artifact tests explicitly double the trusted development validator to check publication and authority boundaries without running predictors. A negative test invokes the real validator and rejects an incomplete/stale receipt. These software contracts are not native acceptance evidence. The actual nominated profile will be recorded only after the complete prospective development report exists.
